# 商业使用、商标与再分发

本项目对外使用“ARM64 Linux 镜像构建”等中性描述。当前技术基线使用 Ubuntu
软件源，并集成本地 SDK 内核、启动组件、驱动和应用，属于独立维护的修改版镜像。
本文说明项目交付规则和未完成事项，不是 Canonical 的授权文件或法律意见。

## 官方政策与使用场景

Canonical 的[知识产权政策第 2–4 节](https://canonical.com/legal/intellectual-property-policy)
区分内部使用、原样再分发及修改版再分发；组件原有开源许可赋予的权利不因此缩减。

| 场景 | 应确认的要求 |
| --- | --- |
| 个人或企业内部使用、修改 | 政策允许内部使用和修改；内部商用不等同于向客户交付镜像。 |
| 原样提供官方镜像 | 与本项目的 SDK 定制镜像不同，不能把修改版标为原样发行。 |
| 对外提供修改版并关联官方商标 | 政策要求 Canonical 批准、认证或提供，并可能需要许可协议。 |
| 对外提供自有名称修改版 | 政策还提出移除、替换商标及重新编译源码生成自有二进制的要求；删除 README 中的名称不是完整处理。具体适用范围应向 Canonical 确认。 |

技术兼容性与来源可以如实说明，但不得暗示官方背书。企业内部使用、公开免费下载、
预装硬件销售、向客户交付及在线提供镜像，应分别按实际分发方式审查。

购买支持服务也不能自行推定获得镜像商标许可；
[服务条款第 4 节](https://canonical.com/legal/ubuntu-pro-service-terms)将商标许可与订单
明确约定的活动范围关联。需要确认本项目的授权路径时，通过
[官方知识产权政策中的联系入口](https://canonical.com/legal/intellectual-property-policy#8-contact-us)
提交实际镜像组成和用途。不要将社区回复或本文当作书面许可。

该声明用于说明来源，不是免责授权。不要写“已获官方授权”“官方认证”“完全无商业

实际使用方式和授权确认另行处理。

## 二进制和开源许可

不同组件的许可分别适用。允许商业使用不等于免除再分发义务；
[GNU 官方 FAQ](https://www.gnu.org/licenses/gpl-faq.en.html#DoesTheGPLAllowMoney)
说明 GPL 软件可以收费分发。分发 GPL 二进制时，须按适用版本履行对应源码等要求，
不能只提供软件包版本号或指向已经失效的上游链接。不同版本及交付方式条件不同，
参阅 [GPLv2 FAQ](https://www.gnu.org/licenses/old-licenses/gpl-2.0-faq.html) 和
[GPLv3 正文](https://www.gnu.org/licenses/gpl.en.html)。

本项目交付应准备以下对应材料：

| 交付物 | 应保留、核对的材料 |
| --- | --- |
| kernel、KO、U-Boot | 对应源码版本、实际应用的 patch、最终配置、必要构建脚本及适用许可；版本号清单不能替代对应源码。 |
| DEB 及修改过的开源程序 | 实际版本、包内 copyright/许可证、修改记录、对应源码及该许可要求的 NOTICE 等材料。 |
| SDK 专有运行库、固件、模型、IQ 数据 | 逐项取得适用于预期用途和分发对象的许可依据；可从 SDK 取得不等于可以公开上传。 |
| 本仓库的脚本、配置、文档 | 确认权利归属及明确的许可证范围；不要用某个第三方包的许可覆盖整个仓库。 |

例如，当前 `package/rknpu2/debian/copyright` 将其预编译运行库、server、测试程序和
模型记为 `Proprietary`。这记录的是现有包声明，**不是已经取得公开再分发许可的证据**。
上传 GitHub Release、Forgejo Packages、CI 附件或交给客户，均要先核对这些输入的权限。
Git 忽略 `artifacts/` 只解决仓库管理，不能代替许可审查。

保留原有版权、作者、许可证及必要的 NOTICE。不得通过删除
`/usr/share/doc/*/copyright`、修改 DEB 元数据或抹去作者来完成所谓“去品牌”。
软件源地址和签名密钥也不能只为删除文字而替换成错误来源。

## 当前完成范围与待办

本次完成 README 产品矩阵、主要文档标题和新发布文案的中性命名，补充来源说明及
社区协作指引。以下项目仍须针对实际商业交付完成，本文没有将其判定为通过：

- 当前未发现仓库顶层统一的 `LICENSE` / `COPYING`。维护者须确认自有代码的许可
  及范围；已有组件 copyright 继续单独适用，公开仓库不等于全仓库获任意再授权。
- 明确修改版镜像的分发和商标授权路径，确认政策中的二进制重编译要求如何适用。
- 核对镜像内的 `/etc/os-release`、登录横幅、Plymouth、GDM、桌面主题、壁纸、logo、
  浏览器入口和软件商店等实际可见标识；本次文档更名未修改这些内容。
- 核对公开仓库名称、网页地址、旧 Release 描述、历史附件名称和截图的品牌使用。
  不重写历史镜像、校验和或验收记录来制造已完成去标识的假象。
- 为各开源二进制准备满足适用许可的对应源码交付材料，并确认专有输入的再分发依据。

商业交付前，负责人应记录实际镜像 SHA256、源码与输入身份、授权文件覆盖范围、
源码提供方式和审查结论。现有 package manifest 可用于建立清单，但不是完整 SBOM、
许可证报告、授权证明或商业合规结论。需要法律判断的部分交由具备相应资格的人员
结合目标市场和具体交付审查。
